Summary

This commit fixes a race condition in cart completion where multiple simultaneous completeCartWorkflow executions could cause duplicate payment refunds. The compensatePaymentIfNeededStep now checks if an order was already placed before refunding a captured payment, preventing stale compensation runs from refunding payments that successfully completed in a later execution.

Step 3: Capture the payment using processPaymentWorkflow. Step 4: Manually trigger a completeCartWorkflow failure (without allowing order placement) and ensure the compensation step runs.

Where It Can Break

  • Payment is captured and order is placed successfully, but the compensation step runs before the order_cart link is written to the database — the check sees no order and incorrectly refunds the payment that should be held for the placed order.
  • Multiple parallel completeCartWorkflow executions on the same payment session cause a race where compensation in one execution refunds the payment while another execution is still trying to place the order, leaving the second order without payment.
  • A stale compensation from a failed workflow attempt runs hours later, the order_cart query returns stale cache data showing no order, and the payment is refunded even though a real order exists in the database.
  • The compensation step refunds the payment but the refund operation fails silently (not logged or propagated), leaving the customer believing their order is cancelled while the merchant's system shows payment refunded but no order.

Edge Cases

  • Captured payment is refunded even though the order was successfully placed, leaving the customer's order without payment while the refund processes.
  • Compensation uses the wrong cart ID or order ID during lookup, causing refund to be skipped for cart_B while cart_A's captured payment is incorrectly refunded.
  • Compensation throws an unhandled exception or crashes, preventing the workflow from completing and potentially blocking order processing.
  • Silent failures where refunds are skipped or errors occur without visibility, making it impossible to audit payment states or debug compensation logic.

Final Verdict

Before approving, QA must verify that captured payments are never refunded once an order is successfully placed, even when cart completion is retried or when compensation runs on stale workflow executions. Test the exact race scenario in the test file: process a payment that triggers order placement, then immediately simulate a late compensation attempt and confirm the payment remains captured and no refund is created. Also verify that legitimate refunds (when no order exists) still work correctly.
