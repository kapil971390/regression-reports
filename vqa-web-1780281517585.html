Summary

This commit adds a guard to the payment compensation step that skips refunding payments if a later cart completion attempt already placed an order. The test validates that when a stale compensation from a failed workflow runs after a successful one, it does not refund or recreate payment sessions for orders that are already placed.

Where It Can Break

  • User places an order via one payment session; a stale compensation from a prior failed attempt incorrectly refunds the captured payment, reversing the transaction even though the order is already placed.
  • The order-existence check query returns stale or incomplete data, causing the compensation to proceed when it should skip, resulting in duplicate refunds or duplicate payment sessions.
  • The refund workflow fails silently due to unhandled errors, leaving the payment in a captured state but logging only a warning, causing the payment to remain unavailable for future orders.
  • Race condition occurs where the compensation checks for order existence, finds none, but by the time it refunds, another request has already placed the order, resulting in refunding an order that was just paid.

Edge Cases

  • The stale compensation incorrectly refunds a payment for an order that is already placed, reversing revenue and leaving the customer's payment in a refunded state despite a completed order.
  • The compensation throws an unhandled exception due to null payment session data, preventing the compensation chain from completing and masking other compensation steps.
  • If the query result is stale or incomplete due to eventual consistency, the compensation may refund a payment seconds before an order is placed for that cart, causing a race condition.
  • Unhandled refund errors cause the compensation chain to abort, preventing other cleanup steps from running and leaving the system in an inconsistent state.

Final Verdict

Before approving, verify that the order-existence check correctly identifies when an order has been placed for a cart, even under race conditions. Test the compensation step with a payment that has already been captured and an order that exists—it must skip the refund entirely and log a warning. Also verify that if the check fails to find an order due to data lag, the error does not cause a silent failure; the refund attempt should either succeed or fail loudly so payment reconciliation teams can investigate.
